# Внесок у MailGrit

**English:** [CONTRIBUTING.md](CONTRIBUTING.md)

Дякуємо за інтерес до внеску в MailGrit! Цей документ пояснює, як зробити
внесок, стандарти, яких ми дотримуємося, та вимогу щодо підписання.

## Швидкий старт

```bash
git clone https://github.com/netreondev/MailGrit.git
cd MailGrit
cargo build -p mailgrit-app-desktop          # build
cargo nextest run --workspace                # tests
cargo clippy --workspace --all-targets --all-features -- -D warnings
```

Потрібен Rust **1.97.1** (зафіксований через `rust-toolchain.toml`, edition 2024).

## Перед відкриттям pull request

- **Спочатку виконайте пошук** серед наявних issues/PR, щоб уникнути дублів.
- **Відкрийте issue** для великих змін або нових функцій, щоб обговорити дизайн
  перед тим, як витрачати час на код.
- **Тримайте PR сфокусованими** — одна логічна зміна на PR полегшує огляд.

## Стандарти коду

MailGrit дотримується суворого, автоматизованого рівня якості. Ваш PR має
пройти все перелічене:

| Перевірка | Команда |
|-----------|---------|
| Форматування | `cargo fmt --all -- --check` |
| Лінти | `cargo clippy --workspace --all-targets --all-features -- -D warnings` |
| Тести | `cargo nextest run --workspace` |
| Док-тести | `cargo test --workspace --doc` |
| Ланцюг постачання | `cargo deny check advisories bans licenses sources` |

Ключові правила:

- **Без `unsafe`** — `unsafe_code = "forbid"` на рівні робочої області. У крейтах
  додатка немає жодних винятків.
- **Без панік у продакшн-коді** — `panic`, `unwrap_used`, `expect_used`,
  `indexing_slicing`, `arithmetic_side_effects` усі мають рівень `deny` (тести
  можуть локально послаблювати їх із задокументованою `reason`).
- **`#![forbid(unsafe_code)]`** встановлено у кожному крейті.
- **Без російської мови** у коментарях, документації чи рядках — проєкт
  документовано лише **англійською та українською**.

## Тон документації

Користувацька документація (README, лендінги, `llms.txt`, нотатки до релізів)
дотримується скромного, фактичного тону. Пишучи чи редагуючи її:

- Описуйте, що робить код, а не що він обіцяє. Уникайте абсолютних тверджень
  («гарантовано», «100%», «завжди працює», «просто працює») — краще
  «зазвичай», «у наших тестах», «залежить від ваших налаштувань».
- Не подавайте сумісність із WAF/проксі як обіцянку; обережно її обмежуйте та
  запрошуйте повідомляти про проблеми в issue.
- Без суперлативів, маркетингового пафосу та випадів на адресу інших
  інструментів чи підходів.
- Пишіть «стандартні криптографічні примітиви», а не «надійна/безпечна
  криптографія» — і не прибирайте наявні чесні застереження (що не зашифровано,
  що не перевірено аудит).
- Слово «аудит» — лише для формальних сторонніх аудитів безпеки. Нотатки до
  релізів констатують факти («CI пройдено на Windows/Linux/macOS на момент
  релізу»), а не вердикти («все зелене», «реліз аудиту»).

## Інструменти верифікації

Окрім перевірок, які має проходити кожен PR, CI виконує такий конвеєр
інструментів (див. [`.github/workflows/ci.yml`](.github/workflows/ci.yml)).
Пункти з позначкою **CI-гейт** ламають збірку; пункти **Release** працюють у
релізному воркфлоу.

| Інструмент | Категорія | Статус | Де |
|------------|-----------|--------|----|
| cargo-deny | Ланцюг постачання | **CI-гейт** | `deny.toml` |
| cargo-audit | Адвізорі вразливостей | **CI-гейт** | `.github/workflows/ci.yml` |
| cargo-vet | Політика аудиту залежностей | **CI-гейт** | `supply-chain/` |
| cargo-auditable | Список залежностей у бінарнику | Release | `release.yml` |
| CycloneDX SBOM | Перелік компонентів | Release | `release.yml` |
| SLSA provenance | Походження збірки | Release | `release.yml` |
| cosign signing | Підписи архівів | Release | `release.yml` |
| Gitleaks | Сканування секретів | **CI-гейт** | `.gitleaks.toml` |
| Semgrep (SAST) | Статичний аналіз | **CI-гейт** | `.semgrepignore` |
| Dependabot | Оновлення залежностей | За розкладом | `.github/dependabot.yml` |
| cargo-fuzz | Фаззинг | **CI-гейт** (регресійний replay + дослідницький) | `fuzz/` + seed-корпус |
| proptest | Тести на основі властивостей | Тестовий набір | `crates/core-csv/tests/` |
| Kani | Обмежена перевірка моделей | **За розкладом** (щотижня + на вимогу) | `crates/*/src/kani_harnesses.rs`, `kani.yml` |
| Miri | Виявлення невизначеної поведінки | **CI-гейт** (кожен пуш) | `ci.yml` |
| cargo-mutants | Мутаційне тестування | **CI-гейт** (кожен пуш) | `ci.yml` |
| cargo-semver-checks | Сумісність API | **CI-гейт** | `ci.yml` |
| criterion | Бенчмарки | Bench (CI компілює) | `crates/*/benches/` |
| cargo-bloat | Звіт про розмір бінарника | Release | `release.yml` |

Нотатки щодо окремих інструментів:

- **`cargo audit`** + **`cargo vet`** — незалежна перевірка адвізорі та політика
  аудиту залежностей. Нова залежність має бути або покрита довіреним імпортом,
  або записана в `supply-chain/audits.toml` / `supply-chain/config.toml`.
  Запустіть `cargo vet suggest`, щоб побачити, що переглянути. Нотатка
  чесності: `cargo vet` розрізняє справжній аудит (у `audits.toml`, де ми
  фактично переглянули крейт — наразі це невеликий набір крипто/сторадж-крейтів)
  і відстежуваний **виняток** (exemption, у `config.toml`, що фіксує: крейт
  *не* перевірено, але дозволено). Значна більшість транзитивного дерева наразі
  покрита винятками, а не власними аудитами; реальна цінність CI-гейту в тому,
  що він **блокує додавання нової, неперевіреної й невиключеної залежності**,
  а не в тому, що він атестує кожну наявну. Додаючи залежність, критичну для
  безпеки (криптографія, сховище, мережа), надавайте перевагу справжньому
  запису в `audits.toml`, а не винятку.
- **Gitleaks** + **Semgrep** — сканування секретів та SAST. Підтримуйте
  `.gitleaks.toml` / `.semgrepignore` актуальними, якщо додаєте нові
  згенеровані/вендорені шляхи.
- **Фазз-регресії** — `fuzz/seeds/` містить закомічені регресійні входи, що
  відтворюються на кожному PR. Якщо ви виправили знайдений фаззером баг,
  додайте seed у `fuzz/seeds/<target>/`.
- **Детермінований тест на витік секретів** —
  `crates/app-desktop/src/webview_secret_leak_tests.rs` перевіряє, що паролі
  ніколи не потрапляють у вивід `tracing`. Якщо додаєте логування біля
  чутливих даних — розширте його.
- **Блокуючі CI-гейти (кожен пуш/PR)** — Miri, cargo-mutants, cargo-fuzz
  (використовують nightly-версію Rust і запускаються на кожному пуші/PR).
  Знахідка ламає PR: Miri-UB, мутант, що вижив, або краш фаззера блокує
  злиття. Виправляйте першопричину (не придушуйте) перед злиттям.
- **Kani (за розкладом, не на кожен пуш)** — обмежена перевірка моделей
  парсерів core-domain живе в `.github/workflows/kani.yml` (щотижневий
  cron + на вимогу `workflow_dispatch`), а НЕ в постійному `ci.yml`.
  Гартфеси охоплюють парсери core-domain, але bootstrap `kani-github-action`
  займає ~90 хв, і таймаут джоби GitHub Actions перетворив би це на
  скасування всього run. Запускайте вручну (`gh workflow run kani.yml`),
  коли змінюєте парсери.

Свідомо **не прийнято** (непридатне для моделі загроз цього проєкту):
JWT-тестування (немає JWT), HTTP/DAST/ZAP (немає сервера, це десктоп-клієнт),
сканування TLS/сертифікатів (TLS обробляє системний webview, Rust TLS-коду
немає), ReDoS-сканування (немає Rust `regex` у коді застосунку) та
дослідницькі формальні інструменти (RefinedRust / rocq-of-rust / GillianRust /
ESBMC-Rust).

## Повідомлення комітів

Використовуйте формат **Conventional Commits**:

```
<type>(<scope>): <short summary in imperative mood>

<optional body — what and why, not how>
```

Приклади: `feat(audit): rotate keys on lock`, `fix(csv): strip UTF-8 BOM before
mapping`, `docs: clarify export encryption`. Тримайте короткий опис у межах ≤ 72
символів.

## Сертифікат походження розробника (DCO)

Щоб гарантувати, що кожен учасник має право подавати свою роботу під ліцензією
MailGrit (MIT OR Apache-2.0), ми вимагаємо **Сертифікат походження розробника**
(Developer Certificate of Origin). Це той самий легковагний процес, що його
використовують ядро Linux та багато проєктів на Rust — **немає CLA для
підписання**, лише трейлер коміту.

**Кожен коміт має бути підписаний** додаванням рядка `Signed-off-by:`. Найпростіший
спосіб — передати `-s` у `git commit`:

```bash
git commit -s -m "feat(audit): rotate keys on lock"
```

Це додає:

```
Signed-off-by: Your Name <you@example.com>
```

Використовуйте своє **справжнє ім'я** та **доступну електронну пошту** (ту саму
особистість, яку ви використовуєте на GitHub). Підписуючи коміт, ви
сертифікуєте таке:

> Сертифікат походження розробника (Developer Certificate of Origin)
> Version 1.1 (Версія 1.1)
>
> Copyright (C) 2004, 2006 The Linux Foundation та її учасники.

> ліцензійного документа, але змінювати його не дозволяється.
>
> Сертифікат походження розробника 1.1

