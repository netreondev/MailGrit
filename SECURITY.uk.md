# Політика безпеки

**English:** [SECURITY.md](SECURITY.md)

## Повідомлення про вразливість

Ми серйозно ставимось до помилок у безпеці. Дякуємо, що допомагаєте покращити
MailGrit — будь ласка, повідомляйте про вразливості **відповідально** та
**приватно**, щоб виправлення можна було підготувати до публічного розкриття.

**Переважний канал:** відкрийте **приватний консультаційний документ з безпеки**
на GitHub: [Повідомити про вразливість](https://github.com/netreondev/MailGrit/security/advisories/new).

Будь ласка, додайте:

- Опис проблеми та її потенційного впливу.
- Кроки для відтворення (мінімальний приклад, якщо можливо).
- Версію MailGrit та операційну систему, на яких ви тестували.
- Будь-яку пропозицію виправлення (за бажанням).

Ми підтвердимо отримання протягом **5 робочих днів** і прагнемо надіслати
попередню оцінку протягом **14 днів**. Будь ласка, **не** розкривайте проблему
публічно, поки не буде випущено виправлення і ви не отримаєте сповіщення.

## Версії, що підтримуються

Лише **останній реліз** отримує виправлення безпеки. Релізи публікуються на
[сторінці релізів](https://github.com/netreondev/MailGrit/releases).

## Обсяг

Ця політика охоплює **вихідний код MailGrit** у цьому репозиторії. Вона
**не** охоплює:

- Сам **iRedAdmin** чи будь-який сторонній поштовий сервер — MailGrit є
  незалежним клієнтом і не афілійований з iRedAdmin.
- Сторонні залежності, які відстежуються через `cargo audit` / `cargo-deny`
  у CI; повідомляйте про них безпосередньо відповідальному супроводжувачу
  крейту та [базі консультацій RustSec](https://rustsec.org/).

## Рівень безпеки

Інженерні рішення MailGrit, пов'язані з безпекою:

- **`unsafe_code = "forbid"`** на рівні робочої області — жодного `unsafe` Rust
  ніде у крейтах додатка (перевіряється в CI через clippy/rustc).
- **Сувора дисципліна лінтів** — `panic`/`unwrap`/`expect`/`indexing_slicing`/
  `arithmetic_side_effects` усі мають рівень `deny`, що зменшує кількість
  панік під час виконання.
- **Ланцюговий журнал аудиту (не зашифрований)** — кожна операція додається до
  ланцюгового (HMAC-SHA256) журналу; команда `verify` перевіряє ланцюг і
  повідомляє про розбіжності (видалені, перевпорядковані чи змінені записи).
  Ланцюг дає перевірку цілісності, а **не** конфіденційність: корисне
  навантаження дії зберігається як є у локальному SQLite-файлі аудиту
  (`mailgrit-audit.sqlite`), **не** зашифрованому під час зберігання; тека
  даних лежить поруч із виконуваним файлом (портативний режим), тож її
  конфіденційність залежить від того, куди ви її поклали. Натомість експорти та
  резервні копії **саме** шифруються потоковим AEAD (XChaCha20-Poly1305).
- **Формування ключа з майстер-пароля** — ключ журналу аудиту виводиться з
  обраного користувачем майстер-пароля через Argon2id (KDF, стійкий до атак
  у пам'яті); пароль ніколи не зберігається.
- **Порівняння за постійний час** для перевірок криптографічної рівності.

## Цілісність ланцюга постачання

CI виконується при кожному push та pull request:

- `cargo deny check advisories bans licenses sources` — відомі вразливості,
  заборонені ліцензії, неавторизовані реєстри/git-джерела.
- `cargo audit` — незалежна перевірка консультацій.
- `cargo vet` — кожна залежність або перевірена нами (криптографія та
  зберігання, див. `supply-chain/audits.toml`), або покривається імпортом
  довіреної сторонньої перевірки (Mozilla / Google / Bytecode Alliance /
  Embark, див. `supply-chain/config.toml` та `supply-chain/imports.lock`),
  або записана як явне відстежуване виключення. Застереження: **виключення** —
  це запис «не перевірено, але дозволено», а не атестація; значна більшість
  транзитивного дерева наразі покривається виключеннями, а не власними
  перевірками. Практична цінність цього гейту в тому, що PR, який додає
  **зовсім нову** залежність — ні перевірену, ні виключену — ламає збірку,
  змушуючи до усвідомленого рішення. Кожне виключення має явну примітку;
  механізму терміну дії для виключень **немає** — cargo-vet (перевірено
  2026-08-16 щодо 0.10.2, найновішого релізу, та upstream-гілки `main`) не
  має поля `expire-date` для виключень (термін дії існує лише для wildcard
  *аудитів*), а невідомі ключі конфігу мовчки відкидаються, коли інструмент
  перезаписує файл. Виключення — це бутстрап-борг, який списують ручним
  рев'ю, а не часово обмежений дозвіл.
- `cargo machete` — гігієна невикористаних залежностей.
- `cargo semver-checks` — сумісність публічного API.
- `gitleaks` — сканує історію git на випадково закомічені секрети.
- `Semgrep` (SAST) — статичний аналіз, сфокусований на JS-ін'єкціях у
  привілейований webview та витоку секретів у журнали `tracing`.

Інструментарій Rust (`1.97.1`) закріплений через `rust-toolchain.toml`.

## Верифікація релізів

Кожен реліз містить матеріали, за якими можна перевірити, звідки бінарний файл
і які залежності він містить. Робочий процес релізу
(`.github/workflows/release.yml`) створює, для кожної платформи:

- **Вбудований перелік залежностей** — `cargo auditable build` компілює повне
  дерево залежностей (назви крейтів + версії + відомі консультації на момент
  збірки) у бінарний файл. Скануйте завантажений бінарний файл без доступу до
  джерельного коду:

  ```bash
  cargo install cargo-audit cargo-auditable
  cargo audit bin ./mailgrit-app-desktop.exe
  ```

- **CycloneDX SBOM** — `mailgrit-sbom-<platform>.cdx.json` додається до
  кожного релізу та фіксує розв'язаний граф залежностей на момент збірки.

- **Атестація походження збірки** — кожен архів несе атестацію походження
  збірки (підписаний in-toto statement із SLSA-предикатом походження),
  створену за допомогою
  [actions/attest-build-provenance](https://github.com/actions/attest-build-provenance)
  keyless-способом через ефемерну OIDC-ідентичність GitHub робочого процесу
  (жодних ключів підписування в репозиторії) і збережену у сховищі атестацій
  артефактів GitHub цього репозиторію. Це замінило сторонній робочий процес
  slsa-github-generator, який більше не працює на поточних образах ранерів.
  Перевірте, що бінарний файл зібрано саме з цього репозиторію:

  ```bash
  # Встановлення: https://cli.github.com/
  gh attestation verify mailgrit-windows-x86_64.zip \
    --repo netreondev/MailGrit
  ```

- **keyless-підписи cosign** — кожен архів (`*.zip` / `*.tar.gz`) несе
  від'єднаний підпис `<archive>.sig` та сертифікат підписування `<archive>.pem`,
  виданий через ефемерну ідентичність Fulcio робочого процесу та зафіксований
  у публічному журналі прозорості Rekor. Перевірте автентичність:

  ```bash
  # Встановлення: https://github.com/sigstore/cosign/releases
  cosign verify-blob \
    --certificate mailgrit-windows-x86_64.zip.pem \
    --signature mailgrit-windows-x86_64.zip.sig \
    --certificate-identity-regexp 'https://github.com/netreondev/MailGrit/.*' \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    mailgrit-windows-x86_64.zip
  ```

Ми радимо не запускати бінарний файл, який не пройшов ці перевірки: вони
підтверджують походження збірки, а не відсутність багів.
